BLUELINE · CASE STUDY RUST · CLI · 2026

Approve the change, not the download

GitHub

Blueline is a supply chain security gate for package installs, written in Rust. It exists because of one sentence: package managers treat installs as transport: fetch, unpack, run. Blueline adds the step they skip.

npx blueline install express@4.21.2

The problem

Your coding agent runs npm install dozens of times a day. Each one pulls tarballs off the registry and executes whatever install scripts came along for the ride. Nobody on earth diffs express 4.21.1 against 4.21.2 when an agent fires the command in a loop.

Attackers know this. The TanStack router worm shipped malicious npm packages carrying valid SLSA L3 provenance. In 2021, ua-parser-js was hijacked and three malicious versions published with a credential stealer in the preinstall script. The fix window was four hours. Agents compress that window to minutes.

How it works

Three steps, in order, before anything touches your machine:

  • Sandboxed extraction. The release tarball is unpacked in isolation, with guards against path traversal, symlinks, and decompression bombs.
  • Delta calculation. The new release is diffed, at line level, against your last verified baseline (stored locally in SQLite). Approved versions become the baseline; the next release only has to explain its delta.
  • Approval gate. A review card renders the change before it lands. High-risk releases block outright; the install halts until a human decides.
BLUELINE REVIEW CARD
─────────────────────────────────────────
package:    express
version:    4.21.2
previous:   4.21.1 (last known-clean)

delta:      +3 files, -1 file
size:       +1.2 KB
author:     expressjs (verified)
permissions: no new binaries
install script: none

changed:    lib/router/index.js (3 lines)
            lib/router/layer.js (1 line, comment only)
            package.json (version bump)

verdict:    ▶ LOW RISK

[a]pprove · [h]old · [d]iff

Around that core loop:

  • blueline mcp: an MCP server, so agents call the review themselves instead of bypassing it
  • blueline ci: a lockfile diff scanner for PRs (package-lock.json, Cargo.lock, requirements.txt), plus a GitHub Action
  • policy-as-code via blueline.toml: advisory thresholds, allowlists, blocklists
  • OSV and GitHub Advisory checks, SLSA/PEP 740 provenance surfacing
  • multi-registry: npm, PyPI (--ecosystem pypi), crates.io

Why you can trust the installer itself

A supply chain tool delivered through the same supply chain it criticizes should hold itself to its own standard:

  • Every binary publishes as an npm package with provenance attestation, and SHA256SUMS attach to each GitHub release.
  • A smoke gate runs before shims publish: the actual shipped artifact must review a real package end-to-end through the npm path. If the artifact can't do its one job, nothing ships.
  • Our own composite Action reviews our own package-lock.json on every pull request.

The scanner also fails closed. Any doubt in parsing, extraction, or verification errors out rather than guessing. Mutation tests are pointed at those boundaries so a regression fails CI instead of failing you.

Honest limits

First installs have no baseline to diff against, so they lean harder on advisories, provenance, and static scanning. Heuristics catch common obfuscation routes but are not proof against everything. If you want lower friction while bootstrapping baselines, there's an allow_unreviewed_baseline rule in blueline.toml.

Try it

npm i -g blueline
blueline review lodash@4.17.21

Prebuilt binaries for Linux (x64 glibc and musl, arm64), macOS (x64, arm64) and Windows (x64, arm64). No Rust toolchain required.

OOT · CASE STUDY RUST · VCS · 2026

A court for code

GitHub

Oot is a governance engine for repos where multiple agents write code. The one-line pitch: git and Jujutsu track lines. Oot holds history so it can govern it.

git clone https://github.com/Epoch-AI-Lab/oot

The problem

Agents now write many of the merges. Research Oot's README cites claims code from semantic conflicts is 26x more likely to be buggy. Meanwhile git's permissions are repo-wide (file-level privacy is awkward), branches and PRs are heavyweight for machine-speed work, and text-based merges can't catch conflicts about meaning rather than lines. Two agents can edit adjacent lines without a textual conflict and still produce a program that does neither thing either of them claimed.

Changes, not commits

The core abstraction is the change: a delta between two snapshots, judged without a checkout or working tree. History lives natively in .oot/, a bare git object database plus a change-id DAG, with parents referenced by change IDs, not commit SHAs.

On top of that sit the governance primitives:

  • Visibility policy. Path- or branch-level rules like private-to, embargo-until, public. Privacy is treated as policy, not crypto.
  • Intent. What a change claims to mean, checked against its actual effects.
  • Dispute. Either visibility (a private path was touched) or meaning (two changes clash on intent).
  • Docket. The record of the dispute, verdict, visibility, and embargo.
  • Verdicts. adjudicated, blocked, embargoed, or cloaked.

How adjudication works

Meaning disputes come from a structural engine built on tree-sitter parse trees across Rust, Go, JavaScript, TypeScript, TSX, and Python. Because it needs no working tree, the engine can run inside an agent's memory isolate.

Git stays the interchange format. A change arrives from a human on git, an agent on Jujutsu, or a model in memory; Oot checks it and prints a docket. Export is byte-identical on round-trip, and GitHub is reached through that export, not a fork of git. Embargoed security fixes follow the pattern git and GitHub already use manually, per OSSF guidance.

oot adjudicate --base-ref main --head-ref feature/auth --repo .
oot adjudicate --source jj --base-ref main --head-ref '@-'
oot update --dry-run
oot docket

Exit code 0 means adjudicated; anything else is nonzero, so CI can gate on it the same way it gates on tests.

Status

Oot is a working seed that dogfoods itself: the repo's own changes are governed by Oot. Already shipped: git and Jujutsu ingestion, visibility policy with embargoes, meaning disputes, dockets, the native store, and import / record / log / status / update / gc / export with byte-identical round-trip and visibility filtering.

On the roadmap, deliberately held back until there are real users: hosted intent scoring (a model comparing claimed intent against the actual diff effect), quiet delivery of embargo notices to maintainers, and signature reuse on rewritten commits.

BLUELINE · V0.2.0 AUG 22, 2026 3 min read

Your agent installs code nobody reads

Blueline v0.2.0 is out, and it's the release where the tool becomes a product. One command and it's on your machine:

npm i -g blueline
npx blueline install express@4.21.2

Prebuilt binaries for linux (x64 glibc and musl, arm64), macOS (x64, arm64) and Windows (x64, arm64). No Rust toolchain required.

The problem hasn't changed

Your coding agent runs npm install dozens of times a day. Each one pulls tarballs off the registry and executes whatever install scripts came along for the ride. Nobody on earth diffs express 4.21.1 against 4.21.2 when an agent fires the command in a loop.

Attackers know this. The TanStack router worm shipped malicious npm packages carrying valid SLSA L3 provenance. In 2021, ua-parser-js was hijacked and three malicious versions published with a credential stealer in the preinstall script. The fix window was four hours. Agents compress that window to minutes.

Package managers treat installs as transport: fetch, unpack, run. Blueline adds the step they skip.

What it does

Blueline extracts the release tarball in an isolated sandbox, computes what changed against your last approved version, and shows you before anything lands:

BLUELINE REVIEW CARD
─────────────────────────────────────────
package:    express
version:    4.21.2
previous:   4.21.1 (last known-clean)

delta:      +3 files, -1 file
size:       +1.2 KB
author:     expressjs (verified)
permissions: no new binaries
install script: none

changed:    lib/router/index.js (3 lines)
            lib/router/layer.js (1 line, comment only)
            package.json (version bump)

verdict:    ▶ LOW RISK

[a]pprove · [h]old · [d]iff

Approve once and that version becomes the baseline. The next release only has to explain its delta. If risk thresholds trip, the install blocks and the workflow halts.

Around that core loop:

  • blueline mcp, an MCP server so agents call the review themselves instead of bypassing it
  • blueline ci, a lockfile diff scanner for PRs, plus a GitHub Action
  • policy-as-code via blueline.toml: advisory thresholds, allowlists, blocklists
  • OSV and GitHub Advisory checks, SLSA provenance surfacing

Why you can trust the installer itself

A supply chain tool delivered through the same supply chain it criticizes should hold itself to its own standard. v0.2.0 does:

  • Every binary publishes as an npm package with provenance attestation.
  • SHA256SUMS attach to each GitHub release.
  • A smoke gate runs before shims publish: the actual shipped artifact must review a real package end-to-end through the npm path. If the artifact can't do its one job, nothing ships.
  • Our own composite Action reviews our own package-lock.json on every pull request.

The scanner also fails closed. Any doubt in parsing, extraction, or verification errors out rather than guessing. We keep mutation tests pointed at those boundaries so a regression fails CI instead of failing you.

Try it

npm i -g blueline
blueline review lodash@4.17.21

Point your agent at the MCP server, or drop the GitHub Action into a repo and let it review lockfile changes on every PR.

Repo and docs: github.com/Epoch-AI-Lab/blueline

Honest limits: first installs have no baseline to diff against, so they lean harder on advisories, provenance, and static scanning. Heuristics catch common obfuscation routes but are not proof against everything. If you want lower friction while bootstrapping baselines, there's an allow_unreviewed_baseline rule in blueline.toml.

Simplicity is the new sophistication

I started building File-Organizer-MCP after watching a NetworkChuck video about Model Context Protocol and Docker's MCP registry. I looked over at my desktop and noticed my Downloads folder had accumulated 8 gigabytes of unorganized screenshots, random zip archives, physics PDFs, and installer binaries.

I wanted an agent to clean it up. But when I looked at the existing filesystem tools, they were built around dumb, low-level primitives: read_file, move_file, list_directory.

The token trap of early MCP tools

The early MCP era had a massive flaw: it was brutal for anyone on a free or limited API budget.

If you give an LLM an 8GB folder with 500 files and tell it to organize them using primitive tools, here is what happens:

  1. The model calls list_directory and dumps 500 filenames into the context window.
  2. It calls read_file on file #1 (5,000 tokens).
  3. It calls create_directory for category A.
  4. It calls move_file to move file #1.
  5. It repeats this loop 500 times.

Every single tool result bloated the context by 5,000 to 10,000 tokens. Prompt caching was barely starting out. Within twenty minutes, you burned through 300,000 tokens and slammed directly into provider rate limits.

I hit this exact wall while recording promotional demo videos for the project. I was using Claude to showcase the tool live, and Anthropic hit me with rate limits in the middle of recording. I was so annoyed by the limits that I decided not to edit them out. I kept the rate limit error in the final video. It broke standard marketing playbooks, but people loved seeing the real struggle.

The conclusion was obvious: let local code handle everything the AI could do except decide the intent. The model should never manage individual file pointers in a loop. It should call one high-level, atomic tool, let local Node.js code batch-process 500 files in 15 milliseconds, and return a clean summary diff. One round trip. 400 tokens total.

The 35,000-line monster

File-Organizer-MCP was my first real open source project. Because I was learning Node.js fs and TypeScript on the fly, I fell into the classic first-project trap: every time I had an idea, I wrote a new service class for it.

Before long, the main branch ballooned into nearly 35,000 lines of code across 27 distinct services:

  • image-metadata.service.ts: 1,403 lines
  • content-analyzer.service.ts: 1,304 lines
  • categorizer.service.ts: 1,246 lines
  • file-signatures.ts: 1,044 lines
  • secure-file-reader.ts: 855 lines
  • content-screening.service.ts: 788 lines
  • Heavy binary dependencies like mammoth (Word document parser) and pdf-parse.
  • A 2,000-line readers/ abstraction layer with custom factories, rate limiters, and audit log queues.
  • A stateful file watcher living directly inside the stdio MCP connection.

The project worked, and users found it valuable (42 stars on GitHub, including one user who asked for external drive mount support). But maintaining it felt like pushing a boulder uphill. Fixing a path validation edge case required navigating three factory classes. When JEE prep picked up, I slapped a maintenance banner on the README and froze feature development.

The vision was right, the implementation was fat

Bundling mammoth and pdf-parse in an MCP package was heavy overkill for local developer tooling. But the underlying idea was not wrong. People do want content-aware organization, they just do not want a 50MB dependency tree that crashes on malformed docx tables.

When I came back to the project to prepare the simplify-v5 PR, I decided to rewrite the architecture from scratch.

The simplify-v5 rethink & stateless MCP 2.0

The new MCP 2.0 specification introduced stateless servers. The old 2025 protocol forced stateful session handshakes, persistent Mcp-Session-Id headers, and in-memory singletons that leaked file descriptors. MCP 2.0 replaced all of that with server/discover, request metadata in _meta, and clean response caching via cacheHints.

I structured the v5 refactor around three hard rules:

  1. The 300-line ceiling: No single file in the repository can cross 300 lines. If a module grows beyond that, it gets split or refactored.
  2. Zero heavy parsers: Dropped mammoth, pdf-parse, and the 2,000-line reader framework. Replaced them with a single hardened core/io/readFile() function with TOCTOU guards and sensitive path checks.
  3. Deterministic grouping over bloated NLP: Rebuilt project-based organization using token rarity and Inverse Document Frequency (IDF). It scans plain text markers and identifier tokens in milliseconds with zero external ML dependencies.
  4. Decoupled background watcher: Moved scheduled directory watching out of the MCP server into a standalone CLI binary (bin/file-organizer-watch.mjs). The core stdio server stays completely stateless.

The Linux migration plot twist

While finishing v5, I migrated my main setup from Windows to Linux. In the process, I forgot to back up my npm recovery codes. I lost access to the original npm account where the package was published.

It was frustrating, but honestly fitting. v5 is a complete rebirth of the project anyway. I created a new publisher account and am publishing the clean v5 package there.

42 stars and the moonshot

File-Organizer-MCP is the first project I ever built. 42 people starred it, gave feedback, and used it daily. My goal for this project has not changed: I want to make it the most reliable, widely downloaded file organizer MCP server in the ecosystem. It is a moonshot, but aim for the stars and land on the moon.

The lesson from v1 through v5 was clear: it is not that the original features were bad, it is that the implementation was fat. Real engineering is not about how many abstraction layers you can add. It is about how many you can strip away while making the tool faster and more dependable.

Appendix: The v5 changelog

Here is the raw changelog excerpt from the chore/simplify-v5 release:

## [5.0.0] - 2026-08-22

### ⚠️ Breaking Changes
- Scheduler is now a standalone bin (bin/file-organizer-watch.mjs). Core stdio server serves 21 tools.
- Content-based tools deleted (organize_smart, organize_by_content). Dropped dependencies: pdf-parse, mammoth.
- Stateless protocol era: clients on 2025-era handshake negotiate via dual-era support.

### 🚀 MCP 2026-07-28 Protocol Support
- Switched to @modelcontextprotocol/server@2.0.0.
- Implements stateless MCP spec: no session handshake, server/discover negotiation, response caching (cacheHints ttlMs: 3600000).

### 🧹 Simplification (simplify-v5)
- No file over 300 lines across the entire codebase.
- 27 services collapsed into core/{path,io,scan,categorize,organize,hash}.
- 2,000-line readers/ framework replaced by core/io/readFile() with TOCTOU guards.
- Schemas reduced from 22 to 4 files. RateLimiter deleted.
- History logger appends directly behind in-process write chain with cross-process lockfile.
